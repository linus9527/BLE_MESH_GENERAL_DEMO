## 1. 文档目的

本文定义第一版 Dashboard 的设备范围、单页布局、传感器展示、水阀控制、串口配置、异常状态、扩展接口和验收标准，可直接指导 Node-RED Flow、Dashboard 组件与 Demo 开发。

底层现有 pH、溶解氧和 ORP 消息继续遵循 [architecture-and-protocol.md](./architecture-and-protocol.md)。页面标签、JSON 字段、格式化、趋势和自动控制计算的逐项关系以 [dashboard-data-mapping.md](./dashboard-data-mapping.md) 为准。水位和水阀协议尚未在现有文档中定义，本文给出建议交互契约，最终字段以固件联调结果为准。

## 2. 已确认范围

### 2.1 第一版拓扑与设备

近期规模为三个 XIAO/BLE Mesh 节点、五个设备。一个 XIAO 可以连接多个不同 Modbus 地址的 RS485 传感器；XIAO 后续固件按地址轮询，但每个传感器仍独立产生一个 JSON 数据包，不能把同一节点上的多个传感器合并为一个报告。

第一版只在 Dashboard 展示以下五个设备：

| 类别 | 设备 | 第一版能力 |
| --- | --- | --- |
| 传感器 | pH | 实时值、温度、mV、状态、历史趋势 |
| 传感器 | ORP | 实时值、温度、漂移、状态、历史趋势 |
| 传感器 | 溶解氧 | 实时值、温度、饱和度、校准状态只读展示、历史趋势 |
| 传感器 | 水位/压力 | 实时值、动态单位、状态、历史趋势；当前单位代码 `7=mH2O` |
| 执行器 | 进水阀 | 继电器开关、自动/手动模式、命令状态和结果反馈 |

DHT11、按键和舵机不属于本版前端范围。仓库中即使仍保留旧固件或旧协议代码，Dashboard 也不展示对应入口。

### 2.2 已确认原则

1. 四个传感器集中在同一个 Dashboard 页面显示。
2. 每张传感器卡同时显示即时值、趋势图和状态。
3. 后续允许增加其他传感器，不应复制一整套硬编码页面。
4. XIAO nRF52840 Sense 负责按多个 RS485 地址逐一采集传感器或通过继电器控制水阀；Dashboard 的控制命令经 USB 网关和 BLE Mesh 下发。
5. 第一版不提供任何传感器校准功能，但代码和配置中必须预留通用校准接口。
6. Node-RED 运行在用户本机环境，不依赖 Codex 内置 Node.js 或 Node-RED 运行环境。
7. 服务启动关键路径不扫描、不探测、不等待 USB 网关；无网关时 Node-RED 和 Dashboard 必须正常启动。
8. Node-RED 启动完成后可以异步尝试上次成功使用的网关一次；识别失败立即回到手动选择，不能阻塞服务，也不能自动遍历全部端口。
9. 首页以资方演示为目标，在 1920×1080 下尽量完整显示四张传感器卡、水阀控制和最近事件；允许纵向滚动。
10. LED 不属于当前需求，只保留通用执行器扩展能力，不制作第一版卡片或 Demo 场景。
11. 页面上的每个读数、状态和判断性文案都必须能追溯到输入字段、持久化状态或明确计算规则；没有业务阈值来源时使用中性文案。

## 3. 用户目标

- 打开 Dashboard 后，在一个页面看见四个传感器的即时值、趋势和状态。
- 在 3 秒内判断网关是否连接、每个传感器是否在线、数据是否新鲜。
- 在 10 秒内找到传感器离线、读取故障、数据不完整或串口静默问题。
- 不使用命令行即可选择 USB 网关串口并建立连接。
- 可以在自动/手动模式间切换；手动模式优先级高于自动液位规则，并明确看到水阀命令发送、网关接受和节点结果。
- 可以查看页面标签与 Mesh/网关 JSON 的映射，并配置自动控制的水位下限和上限。
- 后续增加传感器时复用统一卡片、历史数据和状态逻辑。

## 4. 非目标

- 第一版不提供 pH 或其他传感器校准入口、校准命令和校准结果页。
- 不提供 BLE Mesh 配网、AppKey 绑定、组地址配置和设备地址修改。
- 不提供固件升级、Modbus 参数配置或 Node-RED 进程重启。
- 不在服务启动关键路径扫描串口，不自动遍历所有端口；只允许启动后异步尝试上次成功网关一次。
- 不在第一版提供普通用户新增、删除设备的管理页面。
- 不在缺少物理反馈的情况下声称水阀处于真实打开或关闭状态。

## 5. 信息架构

Dashboard 基础路径保持 `/dashboard`，只设置三个一级页面：

| 页面 | 路径 | 任务 |
| --- | --- | --- |
| 设备总览 | `/dashboard/overview` | 查看四个传感器、控制水阀、查看最新事件 |
| 事件记录 | `/dashboard/events` | 查询设备状态、异常和水阀控制记录 |
| 连接与诊断 | `/dashboard/diagnostics` | 手动配置串口并查看通信诊断 |

“集中在一个画面”解释为所有传感器位于同一个逻辑页面，可以纵向滚动，不要求所有内容强行压缩在一个无滚动的 1080p 视口内。点击传感器卡片在当前页打开详情抽屉，不跳转到单独的传感器页面。

## 6. 设备总览

### 6.1 页面结构

页面从上到下依次为：

1. 顶部栏。
2. 串口连接栏。
3. 全局状态摘要。
4. 四张传感器卡。
5. 一张水阀控制卡。
6. 最近事件。

1920×1080 演示屏使用四列传感器卡，四个主读数、短趋势和状态首屏同时可见；水阀与最近事件位于下一行。1200–1599 px 使用 `2 × 2`，小于 768 px 改为单列。允许纵向滚动，但首页只放关键读数、短趋势和状态，完整字段放入详情抽屉。

### 6.2 顶部栏

顶部栏包括：

- 产品名称，第一版暂用“BLE Mesh 水质监控”。
- 网关状态：未连接、连接中、在线、通信静默或连接错误。
- 在线传感器数，例如“3/4 在线”。
- 未恢复异常数。
- 最后有效消息相对时间，例如“5 秒前”。

点击网关状态进入“连接与诊断”；点击异常数进入“事件记录”并自动筛选未恢复异常。

### 6.3 串口连接栏

串口连接栏默认展开，连接正常后可以折叠成一行。包含：

- 串口下拉框。
- “刷新串口”。
- “连接”或“切换”。
- “断开”。
- 当前状态和错误原因。
- 固定参数摘要：`115200 8N1 · DTR 开启`。

交互规则：

1. Node-RED 服务先完成启动，Dashboard 不等待串口。
2. 启动完成后，后台只对上次成功网关做一次有界异步识别；识别成功则连接，失败则显示“上次网关未找到”，不遍历其他端口、不重试循环、不影响 Dashboard。
3. 用户点击“刷新串口”后才调用一次本机串口枚举。
4. 枚举过程不能阻塞 Node-RED 事件循环，3 秒未完成即结束并提示“串口枚举超时”。
5. 下拉选项显示路径、友好名称、厂商和 VID/PID，例如 `COM24 · Nordic Semiconductor · 1915:521F`。
6. 用户选择端口并点击“连接”后，Node-RED 打开该串口。
7. 串口打开后显示“串口已打开，等待网关数据”；收到合法网关 JSON 后才显示“网关在线”。
8. 5 秒未收到合法 JSON 时保持端口打开，但提示“尚未验证为 BLE Mesh 网关”，允许用户断开或改选其他端口。
9. 端口占用、权限不足或设备拔出时显示明确原因，不能导致 Node-RED 服务退出。
10. 成功连接后保存稳定 USB 身份和端口路径，供下次启动后单次识别。
11. 有水阀命令正在等待结果时，普通用户不能断开或切换串口，并显示禁用原因。

Windows 优先显示 `COMx`；Linux 优先显示 `/dev/serial/by-id/...` 稳定路径。普通用户不能修改波特率、数据位、停止位、校验位和 DTR。

### 6.4 全局状态摘要

只显示三个摘要：在线传感器数、故障/离线数、最后有效消息时间。传感器主读数已经在下方卡片展示，不再增加重复的大数字卡。

### 6.5 传感器卡通用结构

四张传感器卡使用同一骨架：

1. 标题：设备名、状态文字、状态图标。
2. 主读数：数值和单位；无数据时显示 `—`，不能显示 `0`。
3. 次读数：最多三个，按设备注册表配置。
4. 趋势图：最近 15 分钟主读数折线，标出最新值。
5. 数据时间：相对时间；超过 60 秒显示“数据可能已过期”。
6. 设备信息：Mesh 地址、所属节点；默认折叠。
7. “查看详情”：打开当前页详情抽屉。

卡片状态必须同时使用文字、图标和颜色，不能只依赖颜色。

| 状态 | 展示 | 条件 |
| --- | --- | --- |
| 等待数据 | 灰色、`—` | 已连接网关但尚未收到该传感器数据 |
| 数据正常 | 正常强调 | 在线且最近数据有效 |
| 数据不完整 | 黄色提醒 | 同一报告中部分字段缺失 |
| 数据过期 | 黄色提醒 | 超过 60 秒没有新读数，但尚未确认离线 |
| 传感器故障 | 红色故障 | `sensor_error` 或故障状态位 |
| 设备离线 | 红色离线 | `device_offline` 或超时判定 |
| 网关未连接 | 灰色禁用 | 串口未打开或尚无合法网关数据 |

设备离线或网关断开时保留最后有效值和时间，但必须标为“最后有效值”，不得表现为实时值。

### 6.6 四种传感器字段

| 传感器 | 主读数 | 次读数 | 格式 |
| --- | --- | --- | --- |
| pH | `ph` | `temperature_c`、`ph_mv` | pH 2 位，温度/mV 1 位 |
| ORP | `orp_mv` | `temperature_c`、`orp_drift_mv` | 均保留 1 位 |
| 溶解氧 | `dissolved_oxygen_mg_l` | `temperature_c`、`saturation_pct`、校准状态 | DO 2 位，温度 1 位，饱和度整数 |
| 水位/压力 | `value` | `unit`、量程摘要 | 当前单位代码 `7`，JSON 使用 `mH2O`，界面排版为 `mH₂O` |

DO 的 `calibration_status_known=false` 或校准字段为 `null` 时显示“校准状态未知”，不能误显示为“未校准”。第一版只展示设备上报的 DO 校准状态，不提供校准操作。

### 6.7 多地址传感器身份与独立 JSON

同一 XIAO 上的多个 RS485 传感器共享一个 Mesh 节点地址，但 Dashboard 必须独立维护每个传感器的读数、状态、历史和事件。JSON 至少同时包含：

- `node_id`：XIAO/BLE Mesh 节点逻辑 ID。
- `sensor_id`：传感器稳定逻辑 ID，作为 Dashboard 和数据库主键。
- `mesh_addr`：节点 Mesh 地址。
- `rs485_address`：该传感器 Modbus 从站地址。
- `sensor_type`：`ph`、`orp`、`do`、`water_level` 等。

XIAO 按地址串行轮询。一个从站超时、CRC 错误或返回异常码时，只标记对应 `sensor_id` 故障，继续轮询同一 XIAO 上的其他地址。

### 6.8 水位值与单位规则

协议原文确认：单位寄存器 `0x0002` 的代码 `7` 对应 `mH2O`，测量值寄存器是 `0x0004`，小数位寄存器是 `0x0003`。实际值为有符号 `raw_value / 10^decimal_places`。代码 `7` 不是 RS485 从站地址。

建议网关为水位传感器输出：

```json
{
  "type": "water_level_report",
  "node_id": "BLE_MESH_RS485_01",
  "sensor_id": "WATER_LEVEL_01",
  "sensor_type": "water_level",
  "mesh_addr": "0x0008",
  "rs485_address": 4,
  "value": 0.86,
  "unit_code": 7,
  "unit": "mH2O",
  "raw_value": 86,
  "decimal_places": 2,
  "timestamp_ms": 1730000025000
}
```

Node-RED 的单位优先级：

1. 数据包内存在非空且受支持的 `unit`：直接采用并记录来源为 `payload`。
2. 没有 `unit` 但有已知 `unit_code`：按单位代码表映射。
3. 两者都没有：使用设备注册表中的 `defaultUnit`；当前水位默认 `mH2O`。
4. 数据包单位未知或与该指标不兼容：显示“单位未知”，禁止自动水阀规则，不静默套用错误单位。

历史表必须为每条记录保存实际使用的单位。单位发生变化时图表应分段或换算为统一单位，不能把不同单位的数据直接画在同一坐标轴上。自动水阀规则统一在 canonical `mH2O` 下计算。

### 6.9 传感器详情抽屉

详情抽屉包含：

- 完整当前字段。
- 状态、Mesh 地址、最后数据和最后消息时间。
- 主读数历史图。
- 温度或第二读数历史图；没有第二读数时不显示空图。
- 时间范围：近 15 分钟、近 1 小时、近 1 天、近 1 周、近 1 个月。
- 最近异常事件。

时间范围切换时保留原图并显示加载状态；只接受最后一次查询结果。无历史数据时显示“该时间范围内暂无数据”，不能只显示空白坐标系。

第一版抽屉不显示“校准”按钮。未来只有设备注册表声明校准能力且对应适配器可用时，才允许渲染校准入口。

## 7. 水阀控制

### 7.1 水阀卡

第一版为 XIAO 控制继电器的开/关型进水阀。卡片显示：

- 通信状态。
- 控制模式：自动/手动，手动优先级高于自动。
- “最后确认命令：打开/关闭/暂无”。
- 最后命令时间。
- 手动模式下的直接开关。
- 自动模式下的液位下限、上限和当前规则结果。
- 当前命令阶段和失败原因。

如果后续确认使用比例阀，再通过能力配置增加 `0–100%` 目标开度；第一版不提前显示无效的开度控件。

### 7.2 状态语义

水阀没有独立限位、水流或位置反馈时，只能显示“最后确认命令”，不能显示“实际状态”。如果未来增加真实反馈，消息必须包含 `feedback_source=physical_feedback`，界面才能使用“实际打开/实际关闭”。

控制状态机：

```text
idle → sending → accepted → succeeded
                 ↘ failed
                 ↘ unconfirmed
```

- `sending`：Node-RED 正在写入串口。
- `accepted`：网关接受命令，尚未收到水阀节点结果。
- `succeeded`：水阀节点返回执行结果。
- `failed`：端口、网关、Mesh 或节点明确返回失败。
- `unconfirmed`：5 秒未收到最终结果，保留上一条已确认命令。

“网关已接受”不能显示成“水阀已打开”。

### 7.3 自动与手动模式

模式开关具有以下规则：

1. `manual`：停止执行自动液位规则，启用直接水阀开关；人工命令优先级最高。
2. `auto`：禁用直接水阀开关，由水位上下限和滞回规则生成命令。
3. 从自动切换到手动时弹窗确认：“手动模式将暂停液位自动控制，并保留当前阀门指令状态，是否继续？”
4. 从手动切换到自动时弹窗确认：“自动模式会立即根据当前液位判断阀门，当前手动状态可能改变，是否继续？”
5. 用户取消弹窗时，模式开关恢复原状态，不发送任何命令。
6. 模式变化写入事件记录，并包含操作者来源 `dashboard`。
7. Node-RED 自动规则在发送命令前再次检查当前模式；只要模式已是 `manual`，丢弃尚未下发的自动命令。

### 7.4 手动水阀开关

1. 只有网关在线、水阀节点在线、模式为手动且没有待处理命令时，直接开关可用。
2. 从关闭切换到打开时弹出风险确认：“即将打开进水阀，请确认现场管路和液位安全。”用户确认后才发送命令。
3. 从打开切换到关闭不弹窗，应立即发送关闭命令。
4. 命令等待结果期间禁止再次打开，但始终允许再次发送一次关闭命令。
5. 网关未连接、水阀离线、串口正在切换或处于自动模式时，直接开关禁用并显示原因。
6. 每次点击、接受、结果、失败和超时都写入事件记录。

### 7.5 自动液位规则

资方 Demo 将水阀视为进水阀，采用上下限滞回，避免液位在单一阈值附近反复开关：

```text
水位 ≤ 下限 → 打开进水阀
水位 ≥ 上限 → 关闭进水阀
下限 < 水位 < 上限 → 保持最后确认命令
```

上下限是可配置参数，不得写死在 Function 节点或页面脚本中。水阀卡提供“阈值设置”入口，弹窗同时编辑下限和上限：

1. 参数统一以 canonical `mH2O` 保存和计算，页面排版为 `mH₂O`。
2. 两项必须是有限数字，并满足 `下限 < 上限`。
3. 上下限间距不得小于 `0.05 mH2O`，且都必须位于水位传感器已确认的有效量程内。
4. 输入步长优先取水位报告的 `10^-decimal_places`；没有小数位信息时 Demo 使用 `0.01 mH2O`。
5. 自动模式下保存按钮显示“保存并立即应用”，保存后使用当前有效水位立即重新判断；弹窗中明确提示阀门可能改变。
6. 保存成功写入 Node-RED 持久化上下文或配置数据库，并记录修改前值、修改后值、操作者和时间；刷新页面和重启 Node-RED 后仍生效。
7. 仅在没有已保存配置时使用 Demo 默认下限 `0.60 mH2O`、上限 `1.20 mH2O`。默认值只用于演示，不代表现场正式参数。

正式自动控制建议要求连续 `3` 个有效样本落在同一触发区后才下发，以过滤单点毛刺；出现无效样本或回到保持区时连续计数清零。Demo 的低/高液位快捷场景可模拟连续 3 个样本，以便演示。

自动模式安全条件：

- 水位数据超过 60 秒、传感器故障、节点离线、单位未知或无法换算时，暂停自动判断并请求关闭水阀；界面显示“自动控制已降级”。
- 连续相同目标不重复下发命令。
- 自动命令与手动命令使用相同的接受/结果状态机和事件记录。
- 修改阈值后必须重新校验模式、数据新鲜度、单位和量程，不能绕过自动模式安全条件。
- 若最终确认水阀不是进水阀，而是排水阀，必须反转规则，不能只改界面文案。

### 7.6 建议消息契约

水阀消息尚未在现有协议中定义，建议使用可关联的命令 ID：

```json
{
  "type": "valve_command",
  "request_id": "01J5X7M2R8...",
  "device_id": "BLE_MESH_VALVE",
  "source": "manual",
  "state": "open"
}
```

网关接受：

```json
{
  "type": "valve_command_accepted",
  "request_id": "01J5X7M2R8...",
  "device_id": "BLE_MESH_VALVE",
  "source": "manual",
  "state": "open"
}
```

节点结果：

```json
{
  "type": "valve_result",
  "request_id": "01J5X7M2R8...",
  "device_id": "BLE_MESH_VALVE",
  "result": "executed",
  "reported_state": "open",

```

## 8. 本机 Node-RED 与手动串口

### 8.1 运行环境

项目使用用户本机安装的 Node.js、包管理器和 Node-RED 依赖。启动、测试和部署说明不得引用 Codex 自带运行时路径。

建议本机命令保持为：

```powershell
cd node-red
pnpm install
pnpm start
```

如果本机使用 npm，可使用对应 npm 命令。具体 Node.js 版本仍以 `node-red/package.json` 的 `engines` 为准。

### 8.2 启动约束

当前 `node-red/scripts/start.js` 会在启动 Node-RED 前执行串口自动发现；找不到网关时抛错退出。这会使用户无法进入 Dashboard 配置串口，必须取消。

修改后的启动顺序：

1. 校验本机 Node.js 版本。
2. 准备本地数据目录。
3. 立即启动 Node-RED。
4. `serial-port` 配置节点初始为 `enabled=false`，Node-RED 已可对外服务。
5. 启动完成后异步读取上次成功网关身份，只尝试该端口一次，并设置短超时。
6. 识别成功则启用通信；识别失败显示“上次网关未找到”并结束，不循环重试、不阻塞服务。
7. 用户点击“刷新串口”后，才异步调用 `SerialPort.list()` 枚举其他候选。
8. 用户点击“连接”后，通过 `serial control` 节点设置端口并启用通信。

禁止在服务启动路径中：

- 循环等待串口出现。
- 逐个打开端口探测网关。
- 因没有候选串口而退出进程。
- 因端口被占用而终止 Node-RED。
- 同步等待上次网关出现或在后台无限重试。

### 8.3 串口状态机

```text
disconnected
  → enumerating → disconnected
  → connecting → port_open_waiting → online
                         ↘ silent
                         ↘ error
online → disconnecting → disconnected
```

串口枚举和连接都必须有独立超时、错误捕获和最终状态恢复，不能使用会阻塞 Node-RED 事件循环的同步等待。

### 8.4 Node-RED 实现建议

- 使用现有 `node-red-node-serialport` 的 `serial control` 节点动态修改端口和启停状态。
- `serial in`、`serial out` 和 `serial control` 引用同一个 `serial-port` 配置节点。
- 增加本地 `serial-manager` 辅助模块，只负责按用户请求列出端口、格式化 USB 信息和返回可读错误。
- 把上次成功网关的稳定 USB 身份和端口保存在文件型 context 中；服务启动完成后只做一次异步重连尝试。
- 串口错误通过状态消息返回 Dashboard，不抛出到进程顶层。

## 9. 可扩展设备接口

### 9.1 设备注册表

建议增加 `node-red/config/device-registry.json`。通用传感器卡、历史查询和状态处理从注册表读取，不再为每种传感器复制一套 UI 节点。

每个设备至少包含：

| 字段 | 说明 |
| --- | --- |
| `nodeId` | XIAO/BLE Mesh 节点 ID；三个节点之一 |
| `sensorId` / `deviceId` | 传感器或执行器稳定 ID；同一节点上的每个 RS485 地址各自独立 |
| `rs485Address` | RS485 传感器从站地址；执行器可为空 |
| `displayName` | Dashboard 名称 |
| `category` | `sensor` 或 `actuator` |
| `kind` | `ph`、`orp`、`do`、`water_level`、`valve` 等 |
| `reportType` | 网关输出消息类型 |
| `fields` | 字段名、标签、单位、小数位、主次顺序和是否保存历史 |
| `defaultUnit` | 数据包缺少单位时的 Node-RED 回退单位 |
| `capabilities` | `telemetry`、`history`、`alert`、`open_close` 等 |
| `calibration` | 校准适配器配置；第一版统一为 `null` |
| `order` | 首页顺序 |
| `enabled` | 是否展示 |

水位示例中的字段仍需硬件确认：

```json
{
  "nodeId": "BLE_MESH_RS485_01",
  "sensorId": "WATER_LEVEL_01",
  "rs485Address": 4,
  "displayName": "水位",
  "category": "sensor",
  "kind": "water_level",
  "reportType": "water_level_report",
  "fields": [
    {
      "key": "value",
      "label": "水位压力",
      "unitKey": "unit",
      "decimals": 2,
      "primary": true,
      "history": true
    }
  ],
  "defaultUnit": "mH2O",
  "capabilities": ["telemetry", "history", "alert"],
  "calibration": null,
  "order": 40,
  "enabled": true
}
```

### 9.2 校准抽象接口

第一版不实现校准 UI 和命令，但预留统一适配层，不能再次把 pH 校准流程直接写死在 Dashboard 组件中。

建议接口职责：

```text
CalibrationAdapter
├─ getDefinition(device)       返回名称、说明、步骤和输入字段
├─ validate(input, state)      校验设备状态和用户输入
├─ buildCommand(input, id)     生成协议命令
├─ matchAccepted(event, id)    识别网关接受事件
├─ matchResult(event, id)      识别最终结果
└─ formatResult(event)         生成面向用户的结果文案
```

建议 Node-RED 代码位置为 `node-red/lib/calibration-adapters.js`。第一版导出空注册表或基础接口，所有设备配置均为 `calibration: null`，因此 Dashboard 不显示任何校准入口。

未来增加校准功能时：

1. 在设备注册表中声明适配器名称。
2. 为该传感器注册一个 `CalibrationAdapter`。
3. 通用校准抽屉根据 `getDefinition()` 渲染步骤。
4. 所有命令和结果使用 `request_id` 关联。
5. 没有适配器、设备离线或串口未连接时，不显示或禁用校准入口。

第一版验收只验证接口存在、设备默认无校准能力以及未来适配器可以注册；不验证实际校准操作。

## 11. 历史与事件

### 11.1 历史数据

- 四个传感器的主读数都保存历史。
- pH、ORP、DO 的温度继续独立保存。
- 近 15 分钟和近 1 小时使用原始数据。
- 近 1 天、近 1 周和近 1 个月使用聚合数据。
- 任一字段缺失不能阻止其他有效字段入库。
- 水位字段确认后加入相同的历史存储机制。

### 11.2 事件记录

事件表字段：时间、级别、设备、事件、结果、详情。第一版记录：

- 网关连接、断开、通信静默和恢复。
- 串口连接成功、失败和用户断开。
- 设备上线、离线。
- 传感器故障和恢复。
- 水位高/低告警及恢复；规则待确认。
- 水阀自动/手动切换、打开、关闭、网关接受、执行成功、失败和未确认。

首版只查看和筛选，不提供删除、编辑和 CSV 导出。

## 13. 验收标准

1. 未连接 USB 网关时，Node-RED 正常启动并可访问 Dashboard。
2. 服务启动关键路径不调用串口枚举、不循环等待网关、不因缺少端口退出。
3. 服务启动完成后只异步尝试上次成功网关一次；失败不重试循环、不影响 Dashboard。
4. 用户点击“刷新串口”后才枚举其他端口，枚举失败或超时不影响服务。
5. 用户可以选择串口、连接、断开，并看到明确状态和错误原因。
6. 串口打开但未收到合法 JSON 时显示“等待网关数据”，不能显示网关在线。
7. pH、ORP、溶解氧和水位四张卡在同一页面同时可见。
8. 每张传感器卡都包含主读数、15 分钟趋势、状态和更新时间。
9. 首次无数据时数值显示 `—`，不能显示误导性的 `0`。
10. 单个字段缺失时其他有效字段继续显示并写入历史。
11. 设备离线或网关断开时保留最后有效值，并明确标记为非实时数据。
12. 五档历史范围都能加载，快速切换时旧响应不能覆盖新选择。
13. 水位数据包含 `unit` 时优先使用；缺少 `unit` 时按 `unit_code` 映射，再回退设备注册表 `defaultUnit`。
14. 单位代码 `7` 显示为 `mH₂O`，不会与 `rs485_address` 混淆。
15. 同一 XIAO 上多个传感器按 `sensor_id` 和 `rs485_address` 独立显示、入库和判定状态。
16. 水阀“网关接受”和“节点执行结果”是两个可辨识阶段。
17. 自动模式使用上下限滞回；手动接管后自动规则不能再下发命令。
18. 水阀卡可以同时编辑下限和上限，非法数字、下限不小于上限、间距小于 `0.05 mH2O` 或超量程时不能保存。
19. 自动模式保存有效阈值后立即用当前有效水位重算，并记录阈值变更事件；页面刷新或 Node-RED 重启后配置仍存在。
20. 页面可查看 pH、ORP、DO、水位、趋势、状态、水阀模式、阈值和命令结果的字段映射与计算规则。
21. 模式切换和手动打开水阀均有确认弹窗；关闭水阀不弹窗。
22. 没有物理反馈时只显示“最后确认命令”，不显示“实际状态”。
23. 网关未连接、水阀离线或串口切换时，水阀控制不可用并显示原因。
24. 等待水阀结果期间不能重复打开，但允许优先发送关闭命令。
25. 设备注册表新增一个同结构传感器后，可生成卡片和历史入口，不需要复制专用页面。
26. 第一版所有设备 `calibration` 均为 `null`，Dashboard 不出现校准按钮。
27. 校准适配器模块可以注册未来适配器，并具备定义、校验、命令构建和结果匹配接口。
28. DHT11、按键、舵机和 LED 不会出现在页面、导航或 Demo 场景中。
29. 项目文档和启动脚本不引用 Codex 内置运行时路径。
30. 在 360 px 宽度下无页面级横向溢出，仍能查看状态并关闭水阀。
31. 状态不只靠颜色表达，键盘可以访问串口和水阀控件。
32. 现有 Node-RED 流程测试继续通过，并新增无串口启动、串口单次重连、多地址传感器、单位回退、阈值持久化、水阀状态机和校准接口测试。
